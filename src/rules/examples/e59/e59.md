# E0059: Dynamic eval or assert

`eval()` executes a string as PHP code. A string-based `assert()` can also execute code. If any part of that code comes from untrusted input, it can lead to code execution.

## Why it matters

Executing code built at runtime is difficult to validate safely and can turn data into executable behavior.

## Bad example

```php
return eval($code);

assert('$value > 0');
```

## Good example

```php
$callback = $handlers[$name] ?? null;

if ($callback !== null) {
    return $callback();
}

assert($value > 0);
```

## What it checks

- Any `eval()` call
- `assert()` with a string literal or string concatenation

## When it does not report

- `assert()` receives a boolean expression.
- The code uses a callback, dispatch table, or parser instead of `eval()`.

## Model limits

- String expressions stored in variables before being passed to `assert()` are not traced.
- `create_function()` and similar legacy helpers are not checked.
- Boolean assertions are accepted.

## How to fix

- Replace `eval()` with a parser, a dispatch table, or an explicit callback.
- Use a boolean expression in `assert()`.
- Never build executable code from request data.

## Configuration

E0059 is enabled by default and has no section-level switches.

The taint-aware behavior is controlled by a per-rule `taint_mode` setting:

```yaml
rules:
  E0059:
    taint_mode: annotate
```

- `annotate` (default) reports the finding and adds the proven source origin to the message.
- `only` reports only findings reached by proven tainted data.
- `off` keeps the legacy heuristic-only behavior.

See the [rule glossary](rule_glossary.md) for the definition of taint.
