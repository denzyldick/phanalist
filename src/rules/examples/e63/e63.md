# E0063: LDAP injection

This rule reports LDAP search calls where user-controlled input reaches the LDAP filter or query argument. Crafted input can change the meaning of an LDAP filter.

## Why it matters

LDAP injection can affect authentication and directory lookups, potentially allowing unauthorized access, disclosure of directory data, or unintended query results.

## Bad example

```php
$username = $_GET['user'] ?? '';
$filter = "(uid=$username)";
$result = ldap_search($conn, $dn, $filter);
```

If an attacker sends `?user=*)(|(uid=*))`, the filter can be altered to match more entries than intended.

## Good example

```php
$username = $_GET['user'] ?? '';
$filter = "(uid=" . ldap_escape($username, '', LDAP_ESCAPE_FILTER) . ")";
$result = ldap_search($conn, $dn, $filter);
```

`ldap_escape()` with `LDAP_ESCAPE_FILTER` escapes special LDAP filter characters so user input is treated as data.

## What it checks

- `ldap_search()`, `ldap_list()`, and `ldap_read()` calls
- Cases where user-controlled input reaches these calls, based on taint analysis and dynamic-expression heuristics

## When it does not report

- Static LDAP filters with no user-controlled input
- Cases where sanitization or data flow prevents the taint/heuristic model from reporting the sink
- Cases where the model cannot prove the input reaches the call

## How to fix

- Escape user input with `ldap_escape($input, '', LDAP_ESCAPE_FILTER)` before placing it in an LDAP filter.
- Prefer parameterized or library-supported safe query APIs where available.
- Validate input against an expected format when possible.

## Configuration

E0063 is enabled by default. The taint-aware behavior is controlled by a per-rule `taint_mode` setting:

```yaml
rules:
  E0063:
    taint_mode: annotate
```

- `annotate` (default) reports the finding and adds the proven source origin to the message.
- `only` reports only findings reached by proven tainted data.
- `off` keeps the legacy heuristic-only behavior.
