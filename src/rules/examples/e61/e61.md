# E0061: Cross-Site Scripting (XSS)

**In plain English:** Your code takes input from a user and displays it back on a web page without escaping special characters. An attacker can inject JavaScript that runs in other users' browsers when they visit your page.

**Why it matters:** XSS allows attackers to:
- Steal session cookies and hijack user accounts
- Redirect users to malicious sites
- Deface your website
- Perform actions on behalf of the victim

## Bad

```php
echo "Welcome, " . $_GET['name'];
```

If an attacker visits: `?name=<script>alert('hacked')</script>`, your page outputs:
```html
Welcome, <script>alert('hacked')</script>
```
The browser executes the attacker's JavaScript.

## Good

```php
echo "Welcome, " . htmlspecialchars($_GET['name'] ?? '', ENT_QUOTES, 'UTF-8');
```

`htmlspecialchars()` converts `<` to `&lt;`, `>` to `&gt;`, etc., so the browser treats it as text, not executable code.

## What the rule checks

- `echo`, `print`, `printf()`, `vprintf()` calls that output user input directly
- String concatenation involving superglobals (`$_GET`, `$_POST`, etc.) in output

## When it does not report

- Output wrapped in `htmlspecialchars()`, `htmlentities()`, or template engine auto-escaping (Twig, Blade, Latte)
- Static text with no user input

## How to fix

1. **Escape output**, not input. Always escape data when displaying it on a page.
2. Use `htmlspecialchars()` with `ENT_QUOTES` and `'UTF-8'`:
   ```php
   echo htmlspecialchars($userInput, ENT_QUOTES, 'UTF-8');
   ```
3. Better yet, use a template engine with auto-escaping (Twig, Blade, Smarty).

## Configuration

E0061 is enabled by default and has no configuration options.
