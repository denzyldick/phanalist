# E0067: Mail injection

This rule reports mail-sending calls where user-controlled input reaches mail headers, subject, or related arguments. Crafted input can inject additional mail headers.

## Why it matters

Mail injection can allow attackers to abuse a contact form or mail feature to send spam, spoof headers, or add unintended recipients.

## Bad example

```php
$email = $_GET['email'] ?? '';
mail('admin@example.com', 'Contact', $body, "From: $email");
```

If an attacker injects CR/LF characters, they may be able to add extra headers such as `Bcc`.

## Good example

```php
$email = filter_var($_GET['email'] ?? '', FILTER_VALIDATE_EMAIL);
if ($email === false) {
    http_response_code(400);
    exit;
}
mail('admin@example.com', 'Contact', $body, "From: $email");
```

Validate email addresses and strip newline characters from header values before using them.

## What it checks

- `mail()` and `mb_send_mail()` calls
- Cases where user-controlled input reaches these calls, based on taint analysis and dynamic-expression heuristics

## When it does not report

- Mail calls built only from static or trusted data
- Cases where sanitization or data flow prevents the taint/heuristic model from reporting the sink
- Cases where the model cannot prove the input reaches the call

## How to fix

- Validate email addresses with `filter_var($email, FILTER_VALIDATE_EMAIL)`.
- Strip CR and LF characters from header values: `str_replace(["\r", "\n"], "", $input)`.
- Consider using a mail library that handles header construction and escaping safely.

## Configuration

E0067 is enabled by default. The taint-aware behavior is controlled by a per-rule `taint_mode` setting:

```yaml
rules:
  E0067:
    taint_mode: annotate
```

- `annotate` (default) reports the finding and adds the proven source origin to the message.
- `only` reports only findings reached by proven tainted data.
- `off` keeps the legacy heuristic-only behavior.
