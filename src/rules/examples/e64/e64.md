# E0064: XPath injection

This rule reports XML/XPath-related calls where user-controlled input reaches the sink. Crafted input can change how XML is loaded or queried, depending on the API and usage.

## Why it matters

XPath or XML injection can expose unintended data, bypass checks, or cause the application to process attacker-controlled XML content.

## Bad example

```php
$user = $_GET['user'] ?? '';
$query = "//user[login='$user']";
$result = $xpath->query($query);
```

If untrusted input is interpolated into an XPath expression, an attacker may alter the query logic.

## Good example

```php
$user = $_GET['user'] ?? '';
$escaped = str_replace("'", "\\'", $user);
$query = "//user[login='$escaped']";
$result = $xpath->query($query);
```

Escaping or parameterizing user input reduces the risk of changing the query structure. Use the safest API available in your XML stack.

## What it checks

- Method calls named `load` or `loadxml`
- `simplexml_load_string()` calls
- Cases where user-controlled input reaches these calls, based on taint analysis and dynamic-expression heuristics

## When it does not report

- Static XML/XPath inputs with no user-controlled data
- Cases where sanitization or data flow prevents the taint/heuristic model from reporting the sink
- Cases where the model cannot prove the input reaches the call

## How to fix

- Avoid building XPath expressions or XML inputs by concatenating untrusted data.
- Escape or parameterize user input according to the XML/XPath API you use.
- Validate input against an expected format before using it in queries.

## Configuration

E0064 is enabled by default. The taint-aware behavior is controlled by a per-rule `taint_mode` setting:

```yaml
rules:
  E0064:
    taint_mode: annotate
```

- `annotate` (default) reports the finding and adds the proven source origin to the message.
- `only` reports only findings reached by proven tainted data.
- `off` keeps the legacy heuristic-only behavior.
