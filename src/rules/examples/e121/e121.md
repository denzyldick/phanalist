# E0121: Assert with user-controlled string

Calling `assert()` with a string argument that contains user-controlled input can lead to code execution. In older PHP versions, string arguments to `assert()` are evaluated as PHP code.

## Why it matters

`assert()` with a string argument can act as a code execution sink:
- An attacker may be able to execute arbitrary PHP code
- It can lead to full server compromise
- String arguments to `assert()` were deprecated in PHP 7.2 and removed in PHP 8.0

## Bad example

```php
$condition = $_GET['condition'] ?? '';
assert("$condition");
// ?condition=phpinfo() would execute phpinfo()
```

## Good example

```php
// Use assert() only with boolean expressions, never strings
$condition = filter_var($_GET['condition'] ?? '', FILTER_VALIDATE_BOOLEAN);
assert($condition === true);

// Or validate and branch explicitly
$action = $_GET['action'] ?? '';
$allowed = ['enable', 'disable'];
if (!in_array($action, $allowed, true)) {
    http_response_code(400);
    exit;
}
```

## What it checks

- `assert()` calls where the argument is a string containing tainted input
- String concatenation inside `assert()` with user-controlled variables

## When it does not report

- `assert()` with boolean expressions (for example, `assert($x > 0)`)
- `assert()` with literal strings that contain no user input

## How to fix

1. Do not pass user input to `assert()` as a string.
2. Use `assert()` only with boolean expressions.
3. Validate input and use explicit branching instead of dynamic assertions.

## Configuration

E0121 is enabled by default and has no configuration options.
