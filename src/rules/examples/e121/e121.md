# E0121: Assert with user-controlled string

**In plain English:** `assert()` is called with a string argument that contains user-controlled input. In older PHP versions, string arguments to `assert()` are evaluated as PHP code, making this equivalent to `eval()`.

**Why it matters:** `assert()` with a string argument is a code execution sink:
- Attacker can execute arbitrary PHP code
- Full server compromise is possible
- `assert()` with string arguments was deprecated in PHP 7.2 and removed in PHP 8.0

## Bad

```php
$condition = $_GET['condition'] ?? '';
assert("$condition");
// ?condition=phpinfo() would execute phpinfo()
```

## Good

```php
// Use assert() only with boolean expressions, never strings
$condition = filter_var($_GET['condition'] ?? '', FILTER_VALIDATE_BOOLEAN);
assert($condition === true);

// Or validate and branch explicitly
$action = $_GET['action'] ?? '';
$allowed = ['enable', 'disable'];
if (!in_array($action, $allowed, true)) {
    http_response_code(400);
    exit;
}
```

## What the rule checks

- `assert()` calls where the argument is a string containing tainted input
- String concatenation inside `assert()` with user-controlled variables

## When it does not report

- `assert()` with boolean expressions (e.g., `assert($x > 0)`)
- `assert()` with literal strings that contain no user input

## How to fix

1. Never pass user input to `assert()` as a string
2. Use `assert()` only with boolean expressions
3. Validate input and use explicit branching instead of `assert()`

## Configuration

E0121 is enabled by default and has no configuration options.
