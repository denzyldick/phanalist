# E0065: NoSQL Injection

**In plain English:** Your code passes user input directly into a NoSQL database query (like MongoDB). NoSQL databases have their own query language with special operators. An attacker can inject operators that change what your query does.

**Why it matters:** NoSQL injection can:
- Bypass authentication (log in without a password)
- Extract data from your database
- Modify or delete records

## Bad

```php
$username = $_GET['user'] ?? '';
$collection->findOne(['username' => $username]);
```

If an attacker sends: `?user[$ne]=null`, the query becomes:
```php
['username' => ['$ne' => null]]
```
This returns **any user whose username is not null**—potentially the first user in the database, which might be an admin.

## Good

```php
$username = (string)($_GET['user'] ?? '');
$collection->findOne(['username' => $username]);
```

Casting to `string` ensures the input is always a string, not an array or object with MongoDB operators.

## What the rule checks

- MongoDB/PHPLIB `find()`, `findOne()`, `aggregate()` calls with tainted superglobals passed directly as query filters
- `$where` clauses with string interpolation of user input

## When it does not report

- Casting input to expected type (`(string)`, `(int)`) before querying
- Using a query builder that sanitizes NoSQL operators

## How to fix

1. **Cast user input to expected type** before using it in queries:
   ```php
   $username = (string)($_GET['user'] ?? '');
   ```
2. Use a query builder that sanitizes NoSQL operators automatically
3. Never pass raw `$_GET`, `$_POST`, or `$_REQUEST` directly into database queries

## Configuration

E0065 is enabled by default and has no configuration options.

## Related CVE / blog angle

Common in PHP + MongoDB applications. Good differentiator from tools that only cover SQL injection.
