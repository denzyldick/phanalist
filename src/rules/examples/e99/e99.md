# E0099: `var_dump()` / `print_r()` in Production

**In plain English:** `var_dump()`, `print_r()`, `var_export()`, and `debug_zval_dump()` output internal data structures directly to the response, leaking sensitive data like passwords, tokens, database contents, and internal architecture.

**Why it matters:** Debug output left in production can expose:
- Passwords and tokens in database results
- Database structure and schema
- Internal architecture and file paths
- Sensitive configuration values

## Bad

```php
$user = $db->query("SELECT * FROM users WHERE id = ?", [$id])->fetch();
var_dump($user); // leaks password hash, email, etc.
print_r($_POST); // logs all form data including passwords
```

## Good

```php
// Remove debug output, or use a logger with level control:
// error_log(json_encode(['user_id' => $user->id]), 3, '/var/log/app.log');
```

## What the rule checks

- `var_dump()`, `var_export()`, `print_r()`, `debug_zval_dump()` calls in source code

## When it does not report

- Debug output in test files (may be intentional — exclude test paths if needed)
- `error_log()` calls (logging to a file is not the same as outputting to the response)

## How to fix

1. Remove all `var_dump()` / `print_r()` from production code paths
2. Use a proper logging framework (Monolog, Laravel Log, etc.)
3. Log only safe, non-sensitive fields

## Configuration

E0099 is enabled by default and has no configuration options.
