# E0093: Template Injection

Rendering user-controlled input directly as a template source (Twig, Smarty, Blade, etc.) without validation can allow an attacker to inject template expressions that execute code on the server.

## Why it matters

Server-side template injection (SSTI) can lead to:

- Remote code execution
- Reading sensitive files (for example `/etc/passwd`)
- Full server compromise

## Bad example

```php
$template = $_GET['template'] ?? '';
echo $twig->render($template, ['name' => $user->name]);
```

An attacker can send `?template={{7*7}}` or other template expressions to execute code.

## Good example

```php
$template = $_GET['template'] ?? '';
$allowed = ['welcome', 'goodbye', 'reminder'];
if (!in_array($template, $allowed, true)) {
    $template = 'welcome';
}
echo $twig->render($template, ['name' => $user->name]);
```

## What it checks

- `Twig::render()`, `$twig->render()`, `$smarty->display()`, `$blade->render()`, and similar calls with tainted template names or sources
- Template engines rendering user-controlled strings as template source

## When it does not report

- Allowlist validation on template names is recognized
- Template file contents are not analyzed for inline expression injection
- JavaScript template engines (Vue, React) are not covered; those are client-side

## How to fix

1. Use an allowlist of permitted template names.
2. Never pass user input as the template source.
3. Use template engine sandbox modes when they are available.

## Configuration

E0093 is enabled by default.

```yaml
rules:
  E0093:
    template_engines:
      - twig
      - smarty
      - blade
      - latte
    render_methods:
      - render
      - display
      - fetch
      - make
```
