# E0072: Path traversal

Using user-controlled input to build a file path without sanitizing `../` sequences can allow an attacker to read or write files outside the intended directory.

## Why it matters

Path traversal vulnerabilities can allow attackers to:

- Read sensitive files such as `/etc/passwd`, source code, or credentials
- Write arbitrary files to the server
- Achieve remote code execution when combined with other vulnerabilities, such as file upload

## Bad example

```php
$page = $_GET['page'] ?? '';
include __DIR__ . '/pages/' . $page . '.php';
```

If an attacker sends `?page=../../../etc/passwd`, the application may read `/etc/passwd`.

## Good example

```php
$page = $_GET['page'] ?? '';
$allowed = ['home', 'about', 'contact'];
if (!in_array($page, $allowed, true)) {
    $page = 'home';
}
include __DIR__ . '/pages/' . $page . '.php';
```

## What it checks

- `include`, `require`, `file_get_contents()`, `file_put_contents()`, and `fopen()` with paths built from tainted input
- `../` or null byte (`%00`) sequences in user-controlled paths

## When it does not report

- Cases where path components are validated against a whitelist
- Cases where `realpath()` is used to verify that the resolved path starts with the expected directory

## How to fix

1. Use a whitelist of allowed paths or files.
2. Use `realpath()` and verify the result starts with the expected directory prefix.
3. Strip `../` and null bytes from user input.

## Configuration

E0072 is enabled by default and has no configuration options.
