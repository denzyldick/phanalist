# E0068: Eval injection

This rule reports code-evaluation sinks where user-controlled input reaches `eval()` or a string-based `assert()` call. This can allow arbitrary PHP code execution.

## Why it matters

If an attacker can control evaluated code, they may be able to execute commands, read or modify files, access data, or take control of the application environment.

## Bad example

```php
$code = $_GET['code'] ?? '';
eval($code);
```

If an attacker sends `?code=system('id');`, the server executes that code.

## Good example

```php
// Use an explicit allowlist of actions instead of evaluating input.
$action = $_GET['action'] ?? '';
$allowed = ['list', 'view', 'search'];
if (!in_array($action, $allowed, true)) {
    http_response_code(400);
    exit;
}

switch ($action) {
    case 'list':
        listItems();
        break;
    // ...
}
```

## What it checks

- `eval()` calls with user-controlled input
- `assert()` calls with user-controlled string input
- Cases detected through taint analysis and dynamic-expression heuristics

## When it does not report

- `eval()` or `assert()` on static or trusted input that the model does not treat as tainted/dynamic
- `assert()` with a boolean expression
- Cases where the taint or heuristic model cannot prove the input reaches the sink

## How to fix

- Do not pass user input to `eval()` or string-based `assert()`.
- Replace dynamic code execution with an allowlist-based dispatch, parser, or explicit callbacks.
- Use `assert()` only with boolean expressions.

## Configuration

E0068 is enabled by default. The taint-aware behavior is controlled by a per-rule `taint_mode` setting:

```yaml
rules:
  E0068:
    taint_mode: annotate
```

- `annotate` (default) reports the finding and adds the proven source origin to the message.
- `only` reports only findings reached by proven tainted data.
- `off` keeps the legacy heuristic-only behavior.
