# E0090: `session_decode()` on User Data

**In plain English:** Your code calls `session_decode()` on data that may come from the user. `session_decode()` uses PHP's session serialization format, which can instantiate PHP objects and trigger magic methods like `__wakeup()` and `__destruct()`.

**Why it matters:** `session_decode()` is a deserialization sink. Attackers can:
- Instantiate arbitrary PHP classes
- Trigger magic methods (`__wakeup()`, `__destruct()`)
- Achieve object injection and potentially remote code execution

## Bad

```php
$data = $_GET['session_data'] ?? '';
session_decode($data);
```

## Good

```php
// Never decode user-supplied session data
// Use $_SESSION superglobal directly instead
$value = $_SESSION['key'] ?? null;
```

## What the rule checks

- `session_decode()` calls where the argument may originate from `$_GET`, `$_POST`, `$_REQUEST`, `$_COOKIE`, `php://input`

## When it does not report

- `session_decode()` on literal strings or trusted internal variables is not flagged

## How to fix

1. Never pass user-controlled data to `session_decode()`
2. Use the `$_SESSION` superglobal directly

## Configuration

E0090 is enabled by default and has no configuration options.

## Related CVE / blog angle

PHP object injection variant. Related to E0053 (unserialize).
