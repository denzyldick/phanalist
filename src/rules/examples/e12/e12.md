# E0012: Service compatibility with Shared Memory Model

**In plain English:** In long-running PHP runtimes (like RoadRunner, Swoole, or FrankenPHP), application services remain in memory across multiple requests. This rule ensures that services do not mutate their own object properties during request handling, preventing request data leaks between users.

**Why it matters:** In traditional PHP-FPM, memory is wiped clean after every request. In modern workers (Swoole/RoadRunner), a single service instance handles thousands of requests. If a service stores user-specific state in `$this->someProperty = $request->input;`, that state leaks into the next request handled by another user, causing severe security vulnerabilities and data corruption.

## ❌ The Bad Example
```php
namespace App\Service;

class UserService {
    private string $currentUser;

    public function handleRequest(Request $request): void {
        // Mutating $this state in a long-running worker!
        $this->currentUser = $request->get('user'); 
        $this->process();
    }
}
```

## ✅ The Good Example
```php
namespace App\Service;

class UserService {
    // Pass state as method parameters instead of storing in $this
    public function handleRequest(Request $request): void {
        $user = $request->get('user');
        $this->process($user);
    }
}
```

## What the rule checks
- Scans classes in configured namespaces (`App\Service\`, `App\Controller\`).
- Detects assignments to `$this->property` or static properties (`self::$prop`) inside methods (excluding constructors).
- Allows classes that implement a reset interface (e.g., `ResetInterface`) designed to clear state between requests.

## When it does not report
- Classes outside the configured namespaces.
- Classes that implement `ResetInterface`.
- Properties initialized in constructors without being reassigned during request handling methods.

## How to fix
- Make service properties immutable (readonly or set only in constructor).
- Pass request-specific data as parameters to methods rather than storing them in object state.
- Implement a reset interface to clear state if statefulness is strictly required.

## Configuration
```yaml
rules:
  E0012:
    include_namespaces:
      - "App\\Service\\"
      - "App\\Controller\\"
    exclude_namespaces: []
    reset_interfaces:
      - "ResetInterface"
```

### Junior Engineer's Rule of Thumb:
Treat your services as stateless. Never store user request data in `$this->property` inside controllers or services, especially when running modern long-running PHP servers!
