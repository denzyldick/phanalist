# E0118: Log forging via user input

**In plain English:** User input is written to log files without sanitization, allowing an attacker to inject fake log entries or forge audit trails.

**Why it matters:** Log forging can:
- Hide attacks by injecting fake log entries
- Forge audit trails for social engineering
- Corrupt log files, making incident response harder
- Mislead security analysts about what actually happened

## Bad

```php
error_log("User {$_GET['username']} logged in");
// ?username=admin%0d%0aInjection: fake admin login
```

## Good

```php
$username = str_replace(["\r", "\n"], '', $_GET['username'] ?? '');
error_log("User $username logged in");
```

## What the rule checks

- `error_log()`, `syslog()`, `trigger_error()` with tainted superglobals directly interpolated
- Custom log writers (`file_put_contents($log, $user_input)`) with user input

## When it does not report

- `str_replace(["\r", "\n"], '', $input)` is recognized as sanitization
- Cannot analyze custom logging frameworks' internal sanitization

## How to fix

1. Strip `\r` and `\n` from user input before logging
2. Use structured logging (JSON) where newlines are less dangerous
3. Validate and sanitize all input before writing to logs

## Configuration

E0118 is enabled by default and has no configuration options.
