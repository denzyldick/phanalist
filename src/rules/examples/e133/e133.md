# E0133: Header injection via setcookie

Writing user-controlled input to cookie names or values with `setcookie()` or `setrawcookie()` without sanitizing CRLF sequences can allow HTTP header injection.

## Why it matters

Header injection through cookie APIs can:
- Inject additional `Set-Cookie` headers with attacker-controlled values
- Inject other HTTP headers such as `Location` or `Content-Type`
- Contribute to session fixation or cookie manipulation attacks

## Bad example

```php
$name = $_GET['name'] ?? '';
setcookie($name, 'value');
// ?name=session_id%0d%0aSet-Cookie: admin=true
```

## Good example

```php
$name = $_GET['name'] ?? '';
$name = str_replace(["\r", "\n"], '', $name);
$allowed = ['theme', 'lang'];
if (!in_array($name, $allowed, true)) {
    http_response_code(400);
    exit;
}
setcookie($name, 'value', [
    'secure' => true,
    'httponly' => true,
]);
```

## What it checks

- `setcookie()` or `setrawcookie()` calls where the cookie name or value contains tainted input
- Cookie names or values that may contain CRLF sequences

## When it does not report

- `str_replace(["\r", "\n"], '', $input)` is recognized as sanitization
- Cookie names or values are validated against a whitelist

## How to fix

1. Strip `\r` and `\n` from user input before writing it to cookies.
2. Validate cookie names against an allowlist.
3. Set `secure` and `httponly` flags on sensitive cookies where appropriate.

## Configuration

E0133 is enabled by default and has no configuration options.
