# E0133: Header injection via setcookie

**In plain English:** User input is written to cookie headers via `setcookie()` without sanitizing CRLF sequences, allowing an attacker to inject additional HTTP headers or set malicious cookies.

**Why it matters:** Header injection via `setcookie()` can:
- Inject additional `Set-Cookie` headers with malicious values
- Inject other HTTP headers (Location, Content-Type, etc.)
- Perform session fixation or cookie tossing attacks

## Bad

```php
$name = $_GET['name'] ?? '';
setcookie($name, 'value');
// ?name=session_id%0d%0aSet-Cookie: admin=true
```

## Good

```php
$name = $_GET['name'] ?? '';
$name = str_replace(["\r", "\n"], '', $name);
$allowed = ['theme', 'lang'];
if (!in_array($name, $allowed, true)) {
    http_response_code(400);
    exit;
}
setcookie($name, 'value', [
    'secure' => true,
    'httponly' => true,
]);
```

## What the rule checks

- `setcookie()` or `setrawcookie()` calls where the cookie name or value contains tainted input
- Cookie names or values that may contain CRLF sequences

## When it does not report

- `str_replace(["\r", "\n"], '', $input)` is recognized as sanitization
- Whitelist validation of cookie names/values

## How to fix

1. Strip `\r` and `\n` from all user input before writing to cookies
2. Use whitelist validation for cookie names
3. Always set `secure` and `httponly` flags on sensitive cookies

## Configuration

E0133 is enabled by default and has no configuration options.
