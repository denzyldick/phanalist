# E0094: Denial of Service via Regular Expression

User-supplied regular expressions, or regex patterns applied to user input, can cause catastrophic backtracking (ReDoS), consuming CPU and making the application unavailable.

## Why it matters

ReDoS can cause CPU spikes and denial of service. A single malicious request may keep a worker busy for seconds or minutes, exhausting application capacity.

## Bad example

```php
$pattern = '/^(a+)+$/'; // catastrophic backtracking on "aaaaaaaaaaaaaaaaaaaa!"
preg_match($pattern, $_GET['input']);

// or user-supplied pattern:
$pattern = $_GET['regex'] ?? '';
preg_match($pattern, $text);
```

## Good example

```php
// Use simple, bounded patterns
$pattern = '/^[a-z0-9]{1,32}$/';
preg_match($pattern, $_GET['input']);

// Use time-limited regex evaluation if user-supplied patterns are unavoidable
```

## What it checks

- Nested quantifiers in regex patterns, such as `(a+)+`, `(a*)*`, `(a|b)+`
- User-supplied regex patterns passed to `preg_match()`, `preg_replace()`, or `preg_split()`
- `preg_match()` on very long user input without timeout

## When it does not report

- Not all ReDoS patterns can be detected statically; some require runtime analysis
- Simple quantifiers (`a*`, `a+`) are not flagged without nesting

## How to fix

1. Avoid nested quantifiers and alternation in user-facing regex.
2. Use possessive quantifiers or atomic groups where supported by PCRE (for example `*+` and `++`).
3. Validate input length before applying regex.
4. Use a dedicated ReDoS detection library for user-supplied patterns.

## Configuration

E0094 is enabled by default.

```yaml
rules:
  E0094:
    dangerous_patterns:
      - '(a+)+'
      - '(a*)*'
      - '(a|b)+'
      - '(a+)+$'
    max_input_length: 1000
```
