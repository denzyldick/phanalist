# E0094: Denial of service via regular expression

**In plain English:** User-supplied regular expressions, or regex patterns applied to user input, can cause catastrophic backtracking (ReDoS), tying up CPU and causing denial of service.

**Why it matters:** ReDoS causes CPU spikes and denial of service — a single malicious request can tie up a worker for seconds or minutes, exhausting your application's capacity.

## Bad

```php
$pattern = '/^(a+)+$/'; // catastrophic backtracking on "aaaaaaaaaaaaaaaaaaaa!"
preg_match($pattern, $_GET['input']);

// or user-supplied pattern:
$pattern = $_GET['regex'] ?? '';
preg_match($pattern, $text);
```

## Good

```php
// Use simple, bounded patterns
$pattern = '/^[a-z0-9]{1,32}$/';
preg_match($pattern, $_GET['input']);

// Use time-limited regex evaluation if user-supplied patterns are unavoidable
```

## What the rule checks

- Nested quantifiers in regex patterns: `(a+)+`, `(a*)*`, `(a|b)+` etc.
- User-supplied regex patterns passed to `preg_match()`, `preg_replace()`, `preg_split()`
- `preg_match()` on very long user input without timeout

## When it does not report

- Cannot detect all ReDoS patterns statically — some require runtime analysis
- Simple quantifiers (`a*`, `a+`) are not flagged without nesting

## How to fix

1. Avoid nested quantifiers and alternation in user-facing regex
2. Use possessive quantifiers or atomic groups (PCRE supports `*+` and `++`)
3. Validate input length before applying regex
4. Use a dedicated ReDoS detection library for user-supplied patterns

## Configuration

E0094 is enabled by default. Configuration options:

```yaml
rules:
  E0094:
    dangerous_patterns:
      - '(a+)+'
      - '(a*)*'
      - '(a|b)+'
      - '(a+)+$'
    max_input_length: 1000
```
