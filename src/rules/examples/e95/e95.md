# E0095: Insecure comparison

**In plain English:** Secrets (passwords, tokens, API keys, signatures) are compared using `==` or `===` instead of `hash_equals()`, creating a timing side-channel that attackers can exploit.

**Why it matters:** PHP's `==` operator returns early on the first mismatched byte. Attackers can measure response times to:
- Guess secrets one character at a time
- Bypass authentication by guessing API tokens
- Recover signing keys or other secrets

## Bad

```php
if ($provided_api_key == $expected_key) {
    grantAccess();
}
if ($signature == $expected) {
    // VULNERABLE to timing attack
}
```

## Good

```php
if (hash_equals($provided_api_key, $expected_key)) {
    grantAccess();
}
if (hash_equals($signature, $expected)) {
    // Constant-time comparison
}
```

## What the rule checks

- `==` or `===` comparisons where one operand is a secret-like variable (`token`, `secret`, `key`, `password`, `hash`, `signature`, `mac`, `hmac`)
- Both operands must be strings for the timing issue to apply

## When it does not report

- `hash_equals()` is recognized as the safe alternative
- Cannot detect timing attacks on non-string comparisons

## How to fix

1. Use `hash_equals()` for all secret comparisons
2. Never compare passwords directly — use `password_verify()`

## Configuration

E0095 is enabled by default. Configuration options:

```yaml
rules:
  E0095:
    secret_names:
      - token
      - secret
      - key
      - password
      - hash
      - signature
      - mac
      - hmac
      - api_key
      - csrf_token
```
