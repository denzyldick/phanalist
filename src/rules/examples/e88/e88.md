# E0088: Reflection-based injection

Invoking the PHP Reflection API with user-controlled input can allow an attacker to instantiate classes, call methods, or access properties that should not be reachable.

## Why it matters

Reflection-based injection can:

- Instantiate any autoloadable class
- Call private or protected methods
- Access sensitive object properties
- Lead to object injection and remote code execution through gadget chains

## Bad example

```php
$class = $_GET['class'] ?? '';
$reflector = new ReflectionClass($class);
$obj = $reflector->newInstance($_GET['args']);
```

## Good example

```php
$class = $_GET['class'] ?? '';
$allowed = ['User', 'Product', 'Order'];
if (!in_array($class, $allowed, true)) {
    http_response_code(400);
    exit;
}
$reflector = new ReflectionClass($class);
```

## What it checks

- `ReflectionClass`, `ReflectionMethod`, and `ReflectionProperty` constructed from tainted input
- `ReflectionMethod::invoke()` and `ReflectionMethod::invokeArgs()` with tainted method names

## When it does not report

- Cases where class or method names are validated against a whitelist before reflection
- Reflection on static, trusted class names

## How to fix

1. Do not reflect on user-controlled class, method, or property names.
2. Use a whitelist of allowed classes and methods.
3. Use a factory or command pattern instead of dynamic reflection.

## Configuration

E0088 is enabled by default and has no configuration options.
