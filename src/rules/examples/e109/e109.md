# E0109: XSLT Injection

**In plain English:** User-supplied XML or XSLT stylesheets are processed by `XSLTProcessor`. An attacker can execute arbitrary PHP functions via XSLT extensions or read files via the `document()` function.

**Why it matters:** XSLT with PHP extension functions enabled can lead to remote code execution. Even without extensions, XSLT can read local files via the `document()` function.

## Bad

```php
$xsl = $_GET['xsl'] ?? '';
$xml = $_GET['xml'] ?? '';
$proc = new XSLTProcessor();
$proc->registerPHPFunctions(); // enables PHP function calls from XSLT
$proc->importStyleSheet(new DOMDocument());
$proc->transformToXML(new DOMDocument());
```

## Good

```php
// Never register PHP functions with user-supplied XSLT
// Validate XSLT against a strict schema, or avoid XSLT entirely with user input
$proc = new XSLTProcessor();
// Do NOT call registerPHPStylesheet() or registerPHPFunctions()
```

## What the rule checks

- `XSLTProcessor::registerPHPFunctions()` / `registerPHPStylesheet()` calls (inherently dangerous with user input)
- `XSLTProcessor::transformToXML()` / `transformToDoc()` with tainted stylesheet or XML input

## When it does not report

- Cannot determine if XSLT input is user-supplied vs trusted — flagged conservatively
- `registerPHPFunctions()` without user-supplied XSLT may be intentional in admin tools

## How to fix

1. Never call `registerPHPFunctions()` or `registerPHPStylesheet()` with user-controlled XSLT
2. Avoid processing user-supplied XSLT entirely
3. Use XSLT only with trusted, internal stylesheets

## Configuration

E0109 is enabled by default and has no configuration options.
