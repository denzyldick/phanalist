# E0120: Eval with user-controlled string

Calling `eval()` with a string that includes user-controlled input allows arbitrary PHP code execution.

## Why it matters

`eval()` with user input is a critical security risk:
- An attacker can execute arbitrary system commands
- It can lead to full server compromise
- Data on the server may be read, modified, or deleted

## Bad example

```php
$code = $_GET['code'] ?? '';
eval("return $code;");
```

An attacker can send `?code=system('id');`, causing the server to execute the command.

## Good example

```php
// Never eval user input. Use a whitelist-based dispatch instead.
$action = $_GET['action'] ?? '';
$allowed = ['list', 'view', 'search'];
if (!in_array($action, $allowed, true)) {
    http_response_code(400);
    exit;
}
// Handle each allowed action explicitly
switch ($action) {
    case 'list':
        listItems();
        break;
}
```

## What it checks

- `eval()` calls where the string argument contains tainted input
- String concatenation inside `eval()` with user-controlled variables

## When it does not report

- `eval()` on literal strings with no user input
- The rule cannot detect dynamic code construction that bypasses taint tracking

## How to fix

1. Do not pass user input to `eval()`.
2. Replace dynamic code execution with explicit, allowlist-based dispatch.
3. Use a command/action pattern instead of evaluating strings.

## Configuration

E0120 is enabled by default and has no configuration options.
