# E0082: Hardcoded Crypto Key / IV

**In plain English:** Your encryption keys or initialization vectors (IVs) are hardcoded in source code. Anyone with access to the code can decrypt all your encrypted data.

**Why it matters:** Hardcoded keys defeat the purpose of encryption:
- If code is leaked (GitHub, backups), all encrypted data is compromised
- Keys can't be rotated without redeploying code
- Same key is used across all deployments

## Bad

```php
$key = 'my-secret-key-12345'; // hardcoded in source
$iv = '1234567890123456';       // hardcoded IV (also bad — should be random)
$encrypted = openssl_encrypt($data, 'aes-256-cbc', $key, 0, $iv);
```

## Good

```php
$key = getenv('ENCRYPTION_KEY') ?? $_ENV['ENCRYPTION_KEY'] ?? '';
$iv = random_bytes(openssl_cipher_iv_length('aes-256-cbc'));
$encrypted = openssl_encrypt($data, 'aes-256-cbc', $key, 0, $iv);
// Store $iv alongside the ciphertext; never hardcode it
```

## What the rule checks

- String literals assigned to variables used as encryption keys or IVs
- Keys/IVs passed directly as string literals to `openssl_encrypt()`, `openssl_decrypt()`, `hash()`, `crypt()`

## When it does not report

- Keys loaded from environment variables or secrets manager (correct behavior)
- May flag test fixtures with dummy keys — exclude test paths if needed

## How to fix

1. Load keys from environment variables or secrets manager (AWS Secrets Manager, HashiCorp Vault)
2. Generate IVs randomly per encryption operation
3. Never commit keys to version control

## Configuration

E0082 is enabled by default. Configuration options:

```yaml
rules:
  E0082:
    key_variable_names:
      - encryption_key
      - crypto_key
      - secret_key
      - api_key
      - secret
    iv_variable_names:
      - iv
      - initialization_vector
      - nonce
```
