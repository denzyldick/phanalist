# E0126: Missing `Cache-Control` on Sensitive Responses

**In plain English:** Responses containing sensitive data (user profiles, auth pages) lack `Cache-Control` headers, allowing browsers and proxies to cache them.

**Why it matters:** Cached sensitive responses can be read by anyone with access to the browser cache or shared proxy (e.g., public WiFi, corporate proxy).

## Bad

```php
header("Content-Type: application/json");
echo json_encode($userProfile); // no Cache-Control — may be cached
```

## Good

```php
header("Cache-Control: no-store, no-cache, must-revalidate, private");
header("Pragma: no-cache");
header("Content-Type: application/json");
echo json_encode($userProfile);
```

## What the rule checks

- PHP scripts sending responses with user data (`$_SESSION`, `$_POST`, database results) without `Cache-Control: no-store`
- Cannot detect HTML meta cache tags

## When it does not report

- Cannot determine if a response contains "sensitive" data — flagged conservatively on responses that echo user input
- Public/static assets (CSS, JS, images) should NOT have `no-store`

## How to fix

1. `Cache-Control: no-store, private` on authenticated/sensitive pages
2. `Cache-Control: public, max-age=3600` on static assets only
3. Never cache responses containing `$_SESSION` or user-specific data

## Configuration

E0126 is enabled by default. Configuration options:

```yaml
rules:
  E0126:
    sensitive_indicators:
      - $_SESSION
      - $_POST
      - $_COOKIE
      - $_REQUEST
    exclude_paths:
      - public/
      - assets/
      - static/
```

Browser cache leakage. Sensitive data exposure via shared caches.
