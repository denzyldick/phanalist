# E0031: Bounded Formal Verification

E0031 uses bounded symbolic execution and the Z3 SMT solver to check safety
properties in a modeled subset of PHP. For supported operations it encodes the
actual path conditions and values, so a finding comes with a solver-backed
counterexample rather than a heuristic guess.

Proofs are relative to the modeled subset, the configured checks, and the
project's interprocedural summaries. A clean result means no violation was found
in that model; it is not a proof that every possible PHP execution is safe.

## What it does not prove

- Full PHP semantics. Dynamic features such as `eval`, reflection, variable
  variables, dynamic calls and includes, magic methods, and runtime code
  generation are not modeled.
- Heap, object-state, reference, and alias invariants beyond the supported
  function summaries. Nested array shapes are tracked only while they remain
  unambiguous; a write through an untracked path forgets the affected root array.
- Arbitrary loop invariants. Loops are unrolled to a configured bound; this finds
  bugs within that bound but does not prove an inductive invariant for all
  iterations.
- Concurrency and persistent-runtime behavior such as Swoole, RoadRunner, or
  ReactPHP.
- Business, authorization, or security intent. Those properties need to be
  expressed as assertions or contracts before they can be checked.
- Properties whose values remain `Unknown` or unverified. With
  `unknown_policy: report`, E0031 reports a loop accumulator that is too
  unknown to model as a divisor instead of claiming it is safe. A numeric
  accumulator can still be proven nonzero by a subsequent guard such as
  `$count > 0`; a strict guard such as `$count !== 0` remains unverified
  because the accumulator may be an integer or a float. Changing the policy
  suppresses the diagnostic; it does not make the code proven.

## What it checks

- Division, modulo, and `intdiv()` by zero
- `intdiv()` overflow (`PHP_INT_MIN / -1`)
- Negative or out-of-bounds array indexes and string offsets
- Null method calls and property reads
- Return values that contradict their declared return contract or PHPDoc `@return` contract
- PHPDoc `@param` and `@var` refinements such as `positive-int`, `non-zero-int`, and `int<min, max>`, including `@phpstan-*` and `@psalm-*` variants
- `@phpstan-assert` and `@psalm-assert` contracts on functions and methods
- Unreachable statements after `return`, `break`, `continue`, `throw`, or `exit`, including numbered levels and `continue` inside `switch`
- Assertions that can never hold, and assertions that narrow a later property
- Division and access inside `switch` cases and `match` arms, with case guards, empty case-label/`default` fallthrough, and non-empty fallthrough in source order
- Bounded unrolling of `while`, `for`, `do`/`while`, and `foreach` loops, including literal-array key/value targets; for an integer counter initialized to zero before the loop, exit values are merged with the feasible zero-iteration path, so a possibly empty loop leaves it possibly zero and post-loop guarded division is proven safe. Unknown numeric accumulators carry enough type information to prove guards such as `> 0`, `>= 1`, `< 0`, or loose `!= 0`; strict type-sensitive guards remain `unverified`
- Closures and arrow functions, including values captured with `use`; a by-reference capture is forgotten only when the closure body writes it
- `try`/`catch`/`finally` blocks, including catches and finally blocks after early returns
- `never` return contracts on functions and methods, making following code unreachable
- `strlen()` and `count()` when their inputs are known, including derived string and array indexes
- Element reads from tracked literal arrays, including `??` defaults and nested literal shapes
- Nested `isset()` checks over tracked literal arrays, so guarded nested reads do not report missing keys
- Arrays passed by reference to calls, including nested array elements, are forgotten after the call
- Constant-return function and method summaries, plus identity summaries for untyped parameters, including `self::`, `static::`, `parent::`, and `$this->` calls, resolved through class and function `use` imports, aliases, and group imports
- Method summaries and PHPDoc contracts through variables and expressions holding a directly instantiated object (`$helper = new Helper(); $helper->value()`), including classes and contracts declared in other indexed files, plus parameters whose class has no known subclass in the analyzed project; a parameter with a project-local subclass is kept opaque so an override is not mistaken for the base method
- Constant and bounded integer range propagation for private methods and for protected methods whose class has no subclass in the analyzed project, from direct same-class `self::`, `static::`, class-name, or `$this->` calls; includes finite sets when calls pass different literals and named arguments, and evaluates integer expressions such as `$max - $min + 1`, `max()`, `min()`, `abs()`, and `intdiv()`. Classes using traits, first-class callables, dynamic selectors, by-reference parameters, and variadic parameters are skipped. External subclasses of a protected method are outside this project-local model.
- PHPDoc return contracts propagated to call sites: numeric contracts such as `positive-int` and `int<min, max>`, string contracts such as `non-empty-string`, array contracts such as `non-empty-list<T>`, and shaped returns such as `array{name: string, count: int}`. `@param` contracts and shaped parameters are applied while analysing the function body.
- Length-aware values for documented non-empty strings and arrays, so `strlen()` and `count()` can prove derived bounds without treating the value as fully unknown.
- Inherited methods through `extends` and trait `use`, including cross-file inheritance

## Precision and recall benchmark

The `supported_fragment_precision_and_recall` test runs a labelled corpus of
clean and buggy PHP cases through E0031, then reports precision and recall for
the supported fragment. The corpus includes division, modulo, `intdiv()`, array, string,
nullability, return-contract, assertion, unreachable-code, `switch`,
and loop zero-iteration cases. Dedicated benchmark fixtures live in
`src/rules/examples/e31/benchmark/`.

Current result: 46 labelled cases and 46 expected findings, with 0 false
positives and 0 false negatives (100% precision and recall). This is a
regression benchmark for the supported fragment, not a random sample of
arbitrary PHP projects; correctness outside the supported model is not measured
by this score. The `loops` category includes the historical PPOE/pgacc
zero-iteration regression, its unknown-accumulator `unverified` fallback, a
positive-guard counterpart, and a strict-guard soundness case. The `contracts`
category also covers a contract reached through an instantiated object. Run it
with:

```sh
cargo test supported_fragment_precision_and_recall -- --nocapture
```

### Pinned PHPStan reference

The loop fixtures are database-independent: they take an `iterable` and never
open a connection. Compare them with PHPStan **2.3.2**, level `max`, and no
baseline. The pinned configuration is
`src/rules/examples/e31/benchmark/phpstan.neon`; run it with the pinned phar:

```sh
curl -L -o /tmp/phpstan-2.3.2.phar \
  https://github.com/phpstan/phpstan/releases/download/2.3.2/phpstan.phar
php /tmp/phpstan-2.3.2.phar analyse \
  --configuration=src/rules/examples/e31/benchmark/phpstan.neon \
  --no-progress --error-format=table
```

No baseline is used. On PHPStan 2.3.2 at level `max`, both the unguarded and
guarded fixtures pass with no errors: PHPStan does not report the division by
zero on the feasible zero-iteration path. E0031 reports `division-by-zero` on
the unguarded fixture and no finding on the guarded one. The
unknown-accumulator fixtures are E0031-specific: the unguarded and strict-guard
versions report under the default `unknown_policy: report`, while the `> 0`
guard is proven safe. They are not part of the pinned PHPStan config.

## Configuration

```yaml
rules:
  E0031:
    php_version: "8.4"
    check_division: true
    check_modulo: true
    check_intdiv: true
    check_array_index: true
    check_string_offset: true
    check_nullability: true
    check_types: true
    check_assertions: true
    check_unreachable: true
    check_return_contracts: true
    loop_strategy: auto
    unroll_depth: 16
    timeout_ms: 1000
    unknown_policy: report
    max_findings_per_function: 50
```

`check_types` controls PHPDoc `@param`/`@var` refinements. Native PHP type hints
are always honoured. `php_version` is accepted for configuration compatibility;
the modelled semantics are the same across PHP 8.0–8.4. `loop_strategy: none`
limits loop bodies to one iteration; every other value uses `unroll_depth`.
`unknown_policy: report` (the default) reports a solver `unknown` as an
`unverified` finding so it cannot be mistaken for a proof; `ignore` suppresses
that diagnostic.

The verifier is conservative: when it cannot model a value or operation exactly,
it reports the property as unverified instead of claiming it is safe. Assertions
are treated as assumptions: E0031 reports an assertion only when it provably can
never hold, and never reports an assertion merely because its condition is
unknown. Numeric reasoning uses Z3 integer, real, and IEEE-754 float semantics
for the operations that are modeled; it is not a substitute for a full PHP
runtime specification.
