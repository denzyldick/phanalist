# E0129: Second-Order SQL Injection

**In plain English:** User input is stored in the database, then later retrieved and used in a SQL query without re-sanitization. Even if the first insert was safe, the reuse is dangerous.

**Why it matters:** Second-order SQLi bypasses input validation at the point of entry because the malicious payload is stored and executed later.

## Bad

```php
// First request: safe insert
$stmt = $pdo->prepare("INSERT INTO users (username) VALUES (?)");
$stmt->execute([$_GET['username']]);

// Second request: unsafe reuse
$username = $db->query("SELECT username FROM users WHERE id = 1")->fetchColumn();
$result = mysqli_query($conn, "SELECT * FROM profiles WHERE user = '$username'");
```

## Good

```php
// Always use prepared statements, even for data from the database
$stmt = $pdo->prepare("SELECT * FROM profiles WHERE user = ?");
$stmt->execute([$username]);
```

## What the rule checks

- SQL queries (`mysqli_query`, `PDO::query`, etc.) where variables originate from database reads (`fetchColumn`, `fetchAll`, etc.)
- Tainted data flowing from storage to query sink without re-parameterization

## When it does not report

- Requires interprocedural analysis (storage → retrieval → query)
- May flag false positives on trusted database content

## How to fix

1. Always use prepared statements, even for database-sourced data
2. Never assume database content is safe

## Configuration

E0129 is enabled by default and has no configuration options.
