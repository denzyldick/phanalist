# E0108: Dynamic Instantiation

Instantiating a class using a name that comes from user input can allow an attacker to instantiate any autoloadable class, potentially leading to object injection.

## Why it matters

Combined with gadget chains, dynamic class instantiation can:

- Instantiate any autoloadable class
- Trigger object injection via magic methods
- Lead to remote code execution

## Bad example

```php
$class = $_GET['class'] ?? '';
$obj = new $class();
```

## Good example

```php
$class = $_GET['class'] ?? '';
$allowed = ['User', 'Product', 'Order'];
if (!in_array($class, $allowed, true)) {
    http_response_code(400);
    exit;
}
$obj = new $class();
```

## What it checks

- `new $class()` where `$class` comes from superglobal array access
- `ReflectionClass::newInstanceArgs()` with a tainted class name
- `class_exists()` followed by instantiation of user-controlled class names

## When it does not report

- Allowlist-validated class names
- Static class names

## How to fix

1. Use an allowlist of permitted class names.
2. Use a factory pattern instead of dynamic instantiation.
3. Never instantiate classes based directly on user input.

## Configuration

E0108 is enabled by default and has no configuration options.

## Taint engine

This rule is backed by the phanalist taint engine. Instead of guessing whether a variable contains user input, the engine tracks taint from sources to sinks.

- **`TaintMode::Only`** (default): Reports only when a proven taint flow from a source (for example `$_GET`, `$_POST`, superglobals, or request parameters) reaches the sink.
- **`TaintMode::Annotate`**: Reports all findings and adds the proven source origin.
- **`TaintMode::Off`**: Retains legacy heuristic behavior through `taint_support::looks_dynamic` for compatibility.

Every finding carries structured metadata (severity, category, confidence, effort, CWE/OWASP references, fingerprint) and a stable content-based fingerprint independent of line numbers.
