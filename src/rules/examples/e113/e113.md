# E0113: Session regeneration missing

**In plain English:** `set_time_limit(0)` disables PHP's maximum execution time, allowing a script to run indefinitely. Combined with user-triggered endpoints, this enables DoS.

**Why it matters:** An attacker can trigger a long-running script that consumes a worker indefinitely, exhausting all available PHP-FPM workers.

## Bad

```php
set_time_limit(0); // no execution time limit
// user can trigger this endpoint repeatedly
```

## Good

```php
// Rely on php.ini max_execution_time, or set a sane limit
set_time_limit(30); // 30 seconds max
// Or use async job processing for long tasks
```

## What the rule checks

- `set_time_limit(0)` calls
- `ini_set('max_execution_time', '0')`

## When it does not report

- `set_time_limit()` in CLI scripts (daemons, workers) may be intentional
- Cannot distinguish web request context from CLI context

## How to fix

1. Remove `set_time_limit(0)` from web request handlers
2. Use async job queues for long-running tasks
3. Set `max_execution_time` in php.ini (e.g., 30 seconds)

## Configuration

E0113 is enabled by default. Configuration options:

```yaml
rules:
  E0113:
    exclude_paths:
      - scripts/
      - workers/
      - commands/
```

Execution time DoS. Simple but effective against PHP-FPM worker pools.
