# E0014: Law of Demeter

The Law of Demeter discourages reaching through one object to access another object's internals. In practice, this rule flags method chains that navigate through unrelated objects.

## Why it matters

Long call chains like `$a->getB()->getC()->doSomething()` tightly couple code to the structure of multiple objects. Small changes in one class can ripple through callers, making code harder to change and test.

## Bad example

```php
class OrderProcessor {
    public function process(Order $order): void {
        // Reaches through Order to Customer, then through Customer to Wallet.
        $wallet = $order->getCustomer()->getWallet();

        if ($wallet->getBalance() > $order->getTotal()) {
            $wallet->deduct($order->getTotal());
        }
    }
}
```

## Good example

```php
class OrderProcessor {
    public function process(Order $order): void {
        // Talk directly to the Order object passed as a parameter.
        if ($order->canBePaid()) {
            $order->pay();
        }
    }
}
```

## What it checks

- Method chaining that violates the Law of Demeter.
- A method should generally call methods on: `$this`, objects created inside the method, objects passed as parameters, or direct properties of the class.

## When it does not report

- Calls that stay within the allowed collaborators described above.
- Chained calls that do not violate the rule's Law of Demeter checks.

## How to fix

- Ask the immediate collaborator to perform the operation instead of traversing its internal objects.
- Add a method on the direct object that encapsulates the behavior you need.
- Reduce chains such as `$a->b()->c()` by moving logic closer to the data it operates on.

## Configuration

There is no configurable threshold for this rule. Chained method calls that violate the Law of Demeter are flagged.
