# E0132: Header injection via header

**In plain English:** User input is written to HTTP headers via `header()` without sanitizing CRLF sequences (`\r\n`), allowing an attacker to inject additional headers or split the HTTP response.

**Why it matters:** Header injection can:
- Inject malicious headers (Set-Cookie, Location, Content-Type, etc.)
- Perform cache poisoning
- Perform cross-site scripting (XSS)
- Bypass security controls

## Bad

```php
$status = $_GET['status'] ?? '';
header("X-Custom-Status: $status");
// ?status=ok%0d%0aSet-Cookie: session=evil
```

## Good

```php
$status = $_GET['status'] ?? '';
$status = str_replace(["\r", "\n"], '', $status);
$allowed = ['ok', 'error', 'pending'];
if (!in_array($status, $allowed, true)) {
    $status = 'ok';
}
header("X-Custom-Status: $status");
```

## What the rule checks

- `header()` calls with tainted input that may contain CRLF sequences
- `header()` calls where user input is interpolated into the header value

## When it does not report

- `str_replace(["\r", "\n"], '', $input)` is recognized as sanitization
- Whitelist validation of header values

## How to fix

1. Strip `\r` and `\n` from all user input before writing to headers
2. Use whitelist validation for header values
3. Never include raw user input in `header()` calls

## Configuration

E0132 is enabled by default and has no configuration options.
