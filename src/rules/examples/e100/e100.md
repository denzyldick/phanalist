# E0100: `debug_backtrace()` Output to User

**In plain English:** `debug_backtrace()` returns function call history with file paths, line numbers, and arguments. Returning this to users leaks internal code structure.

**Why it matters:** Backtraces reveal:
- File paths and directory structure
- Class names and method names
- Line numbers
- Sometimes argument values
- All useful for planning targeted attacks

## Bad

```php
echo json_encode(debug_backtrace());
echo debug_print_backtrace();
```

## Good

```php
// Log internally instead of returning to user
error_log(print_r(debug_backtrace(DEBUG_BACKTRACE_IGNORE_ARGS), true));
http_response_code(500);
echo 'An error occurred.';
```

## What the rule checks

- `debug_backtrace()`, `debug_print_backtrace()` results echoed, printed, or returned in HTTP responses
- `Exception::getTraceAsString()` output to user without sanitization

## When it does not report

- Logging backtrace internally (error_log) is not flagged
- Cannot determine if output is captured in a response vs logged

## How to fix

1. Log backtraces internally with `error_log()`
2. Return generic error messages to users
3. Set `display_errors = Off` in production

## Configuration

E0100 is enabled by default and has no configuration options.

## Related CVE / blog angle

Stack trace disclosure. Good for showing error handling best practices.
