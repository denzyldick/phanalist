E0132 security major

Header injection via header

Writing user-controlled input to HTTP headers with `header()` without sanitizing CRLF sequences (`\r\n`) can allow HTTP header injection.

Try in Playground All rules GitHub

Writing user-controlled input to HTTP headers with header() without sanitizing CRLF sequences (\r\n) can allow HTTP header injection.

Why it matters

Header injection can:

  • Inject malicious headers such as Set-Cookie, Location, or Content-Type
  • Enable cache poisoning
  • Contribute to cross-site scripting (XSS) in some contexts
  • Bypass security controls that rely on header values

Bad example

$status = $_GET['status'] ?? '';
header("X-Custom-Status: $status");
// ?status=ok%0d%0aSet-Cookie: session=evil

Good example

$status = $_GET['status'] ?? '';
$status = str_replace(["\r", "\n"], '', $status);
$allowed = ['ok', 'error', 'pending'];
if (!in_array($status, $allowed, true)) {
    $status = 'ok';
}
header("X-Custom-Status: $status");

What it checks

  • header() calls with tainted input that may contain CRLF sequences
  • header() calls where user input is interpolated into the header value

When it does not report

  • str_replace(["\r", "\n"], '', $input) is recognized as sanitization
  • Header values are validated against a whitelist

How to fix

  1. Strip \r and \n from user input before writing it to headers.
  2. Validate header values against an allowlist when possible.
  3. Avoid including raw user input in header() calls.

Configuration

E0132 is enabled by default and has no configuration options.
