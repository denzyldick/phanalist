E0054 security major

Dynamic variable creation

`extract()` and variable variables such as `$$name` create local variable names from runtime data. This makes code harder to follow and can allow unexpected keys to overwrite local variables.

extract() and variable variables such as $$name create local variable names from runtime data. This makes code harder to follow and can allow unexpected keys to overwrite local variables.

Why it matters

Unexpected variable creation can make function behavior difficult to understand and, when request data is involved, can overwrite security-sensitive local state.

Bad example

extract($_POST);

$$name = 'value';
${$key} = 'value';

Good example

$name = $input['name'] ?? '';
$email = $input['email'] ?? '';

return compact('name', 'email');

What it checks

  • extract($data) calls
  • Indirect variables such as ${$name}
  • Nested variables such as $$name and $$$name

When it does not report

  • Variables are assigned explicitly.
  • Values are read from an array with a key, such as $input['name'].
  • compact() is used.
  • Dynamic property and method names are used; this rule only checks local variable creation.

Model limits

  • The rule reports the construct, not whether the input is untrusted.
  • extract() is reported even with EXTR_SKIP or EXTR_PREFIX_ALL.

How to fix

  • Read the keys you expect explicitly.
  • Use an array or a small DTO instead of creating variables dynamically.
  • Avoid extract(), especially with request data.
  • If you need a map, use an explicit allowlist of keys.

Configuration

E0054 is enabled by default and has no section-level switches.

The taint-aware behavior is controlled by a per-rule taint_mode setting:

rules:
  E0054:
    taint_mode: annotate
  • annotate (default) reports the finding and adds the proven source origin to the message.
  • only reports only findings reached by proven tainted data.
  • off keeps the legacy heuristic-only behavior.

See the rule glossary for the definition of taint.
