E0046 resource major

Input-Controlled Cardinality

This rule reports request-controlled values that reach loops, allocation sinks, or callees without a bound. Cardinality is separate from taint: a value may be tainted without controlling collection size, and an input-controlled collection may contain ordinary strings.

This rule reports request-controlled values that reach loops, allocation sinks, or callees without a bound. Cardinality is separate from taint: a value may be tainted without controlling collection size, and an input-controlled collection may contain ordinary strings.

Why it matters

When user input controls how many times code loops or how much memory is allocated, a large or unexpected value can cause excessive CPU use, memory growth, or denial of service. Adding an explicit bound or validation step makes the cost predictable.

Bad example

<?php
function loadAll(PDO $db): array
{
    return $db->query('SELECT * FROM users')->fetchAll(); // unbounded
}

Good example

<?php
function loadPage(PDO $db, int $limit, int $offset): array
{
    $stmt = $db->prepare('SELECT * FROM users LIMIT ? OFFSET ?');
    $stmt->execute([$limit, $offset]);
    return $stmt->fetchAll();
}

What it checks

  • Superglobals $_GET, $_POST, $_REQUEST, $_COOKIE, and $_FILES
  • Request-relevant $_SERVER keys such as HTTP_*, REQUEST_*, PHP_AUTH_*, QUERY_STRING, and PATH_INFO; iterating the whole $_SERVER array is treated as server metadata
  • $argv when include_cli_input is enabled
  • Results of filter_input(), apache_request_headers(), and getallheaders()
  • readline() when include_cli_input is enabled
  • file_get_contents('php://input')
  • Heuristic request accessors named input, query, post, get, all, json, file, cookie, header, or param
  • Request-controlled values used as loop bounds
  • Request-controlled values passed to allocation sinks such as str_repeat(), range(), array_fill(), array_pad(), str_split(), explode(), and preg_split()
  • Request-controlled arguments passed to local functions or methods whose resource summary iterates or allocates in proportion to that argument

Findings identify the source, such as $_GET or php://input, and the sink. They do not claim that the input is malicious; they identify a missing bound or validation step.

When it does not report

The rule uses a conservative taint-and-size model, so some cases are not reported or may be reported conservatively:

  • Values transformed through helpers without a resource summary lose their cardinality information
  • Arrays selected by dynamic keys are treated as unknown-sized input collections when the base array is request-controlled
  • A loop bound capped by a comparison guard is treated as bounded on that path; guards in unrelated branches are not applied
  • Validation through custom code is not recognized unless it establishes a recognized cap
  • Request accessors are recognized by name, so a non-request method with one of the listed names may be treated as a source
  • Input read through custom stream wrappers, database results, or message queues is not tracked
  • CLI input is controlled by include_cli_input; set it to true when the application processes command-line arguments
  • Environment variables and whole-array $_SERVER iteration are treated as trusted server metadata, not request cardinality
  • Recursive and higher-order data flow is summarized conservatively

How to fix

  • Validate request-controlled sizes before using them as loop bounds or allocation sizes.
  • Apply an explicit maximum, such as min($count, $limit) or a range check that rejects oversized input.
  • For request-controlled collections, limit the number of items processed or paginate the work.
  • When passing input to a helper, ensure the helper enforces a bound or has a resource summary that reflects the bound.

Configuration

    runtime_threshold: quadratic

    retained_element_bytes: 32
    report_input_cardinality: true

    max_findings_per_function: 20
  • Set report_input_cardinality: false to suppress E0046 findings while keeping E0044 and E0045 active.
  • max_findings_per_function limits duplicate findings in one function body.
