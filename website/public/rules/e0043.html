Stream Resource Used After Close

Reports stream resources that are read, written, or closed after they have already been closed.

Try in Playground All rules GitHub

Reports stream resources that are read, written, or closed after they have already been closed.

Why it matters

Using a closed stream can cause runtime warnings/errors and indicates incorrect resource lifecycle management. This rule uses Phanalist's bounded formal verification engine (Z3-backed) to detect feasible use-after-close paths.

Bad example

<?php
function readFile(string $path): string
{
    $h = fopen($path, 'r');
    fclose($h);
    return fread($h, 100); // used after close
}

Good example

<?php
function readFile(string $path): string
{
    $h = fopen($path, 'r');
    if ($h === false) {
        return '';
    }
    $data = fread($h, 100);
    fclose($h);

    return $data === false ? '' : $data;
}

What it checks

  • fread() or fwrite() on a stream that was closed on every feasible path
  • fread() or fwrite() on a stream that may have been closed on another path
  • fclose() on a stream that was already closed, or may already have been closed
  • Direct aliases created with $alias = $stream, because both names refer to the same tracked resource
  • Branch and loop joins where one path closes the stream and another leaves it open; these produce a "may have been closed" finding
  • Reopening a variable with another direct fopen() resets its lifecycle state

Model limits

E0043 tracks only resources assigned directly from fopen() and used directly by fclose(), fread(), or fwrite(). It assumes fopen() succeeds unless a later guard or contract narrows the value.

The following are not tracked and can cause missed findings:

  • Resources returned by helpers, methods, or other functions
  • Resources stored in object properties, array elements, or static properties
  • Resources selected by a conditional expression or passed through an unmodeled wrapper
  • Other stream operations such as fseek(), ftell(), fpassthru(), or stream_*() functions
  • Stream wrappers, socket resources, and runtime-specific resource lifetimes

Unknown function, method, and static calls with a tracked stream argument invalidate that stream's state, because the call may close it. This is conservative: it can miss a later use-after-close rather than report a false positive. Direct aliases share the same resource identity, but reassigning a reference alias to a different resource is not propagated back to the original name.

How to fix

  • Close each stream exactly once, on all relevant paths.
  • Avoid reading/writing after fclose(), including through aliases.
  • Reopen into a new variable or reset lifecycle clearly when a stream is reopened.
  • Make branch and loop close behavior explicit so all paths have a clear resource state.
