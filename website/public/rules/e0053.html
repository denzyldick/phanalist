E0053 security critical

Unserialize without allowed_classes

`unserialize()` can create objects of classes named inside the input. If untrusted input controls that data, it may trigger dangerous `__wakeup()` or `__destruct()` behavior in classes loaded by the application. This is commonly called object injection.

unserialize() can create objects of classes named inside the input. If untrusted input controls that data, it may trigger dangerous __wakeup() or __destruct() behavior in classes loaded by the application. This is commonly called object injection.

Why it matters

Object injection can lead to unexpected side effects, including file writes, command execution, or other security issues, depending on which classes are available.

Bad example

$cart = unserialize($_COOKIE['cart']);
$cart = unserialize($payload, []);
$cart = unserialize($payload, ['allowed_classes' => true]);

Good example

$cart = unserialize($payload, ['allowed_classes' => false]);

$dto = unserialize($payload, [
    'allowed_classes' => [Cart::class, CartItem::class],
]);

allowed_classes => false prevents object creation and allows only arrays and scalars. A list allows only the classes you name.

What it checks

  • unserialize($payload) with no options argument
  • A literal options array without an allowed_classes key
  • allowed_classes => true, which explicitly allows every class
  • Named arguments such as unserialize(data: $payload, options: [...])

When it does not report

  • allowed_classes is false or a list of class names.
  • The options argument is not a literal array, because the rule cannot prove the key is absent.
  • The input is a literal serialized string.
  • The input is unserialize(serialize($value)), a local round-trip.

Model limits

  • Only literal options arrays are inspected.
  • The rule does not check whether the trusted class list is safe.

How to fix

  • Prefer JSON or another data-only format.
  • If you must use unserialize(), set allowed_classes to false or to a short list of expected classes.
  • Do not pass request data directly to unserialize().

Configuration

E0053 is enabled by default and has no section-level switches.

The taint-aware behavior is controlled by a per-rule taint_mode setting:

rules:
  E0053:
    taint_mode: annotate
  • annotate (default) reports the finding and adds the proven source origin to the message.
  • only reports only findings reached by proven tainted data.
  • off keeps the legacy heuristic-only behavior.

See the rule glossary for the definition of taint.
