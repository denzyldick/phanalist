E0069 security critical

Unsafe deserialization

Passing untrusted data to `unserialize()` or similar deserialization functions can instantiate arbitrary PHP objects and trigger magic methods such as `__wakeup()` and `__destruct()`.

Passing untrusted data to unserialize() or similar deserialization functions can instantiate arbitrary PHP objects and trigger magic methods such as __wakeup() and __destruct().

Why it matters

PHP object injection is a critical vulnerability. A crafted serialized payload can:

  • Trigger magic methods when unserialized
  • Execute code through gadget chains in loaded classes
  • Read, modify, or delete files
  • Lead to remote code execution

Bad example

$data = $_GET['data'] ?? '';
$result = unserialize($data);

An attacker can send a malicious serialized payload that triggers __wakeup() or __destruct() in a loaded class.

Good example

// Use JSON instead of PHP serialization for untrusted data
$data = $_GET['json'] ?? '';
$result = json_decode($data, true);
if (json_last_error() !== JSON_ERROR_NONE) {
    http_response_code(400);
    exit;
}

What it checks

  • unserialize() calls with tainted input from $_GET, $_POST, $_REQUEST, $_COOKIE, or php://input
  • session_decode() with user-controlled data

When it does not report

  • unserialize() on literal strings or trusted internal variables
  • unserialize() with the allowed_classes option set to false or a restrictive array

How to fix

  1. Do not pass user-controlled data to unserialize().
  2. Use JSON (json_decode() / json_encode()) instead of PHP serialization for untrusted data.
  3. If you must use unserialize(), pass ['allowed_classes' => false] to prevent object instantiation.

Configuration

E0069 is enabled by default and has no configuration options.
