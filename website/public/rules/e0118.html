E0118 security major

Log forging via user input

Writing unsanitized user input to logs can allow log forging, where an attacker injects fake log entries or corrupts log structure.

Writing unsanitized user input to logs can allow log forging, where an attacker injects fake log entries or corrupts log structure.

Why it matters

Log forging can:

  • Hide malicious activity by injecting misleading log entries
  • Create false audit trail records
  • Corrupt log files and make incident response harder
  • Mislead anyone investigating system behavior

Bad example

error_log("User {$_GET['username']} logged in");
// ?username=admin%0d%0aInjection: fake admin login

Good example

$username = str_replace(["\r", "\n"], '', $_GET['username'] ?? '');
error_log("User $username logged in");

What it checks

  • error_log(), syslog(), trigger_error() with tainted superglobals directly interpolated
  • Custom log writers such as file_put_contents($log, $user_input) with user input

When it does not report

  • str_replace(["\r", "\n"], '', $input) is recognized as sanitization
  • The rule cannot analyze custom logging frameworks' internal sanitization

How to fix

  1. Strip \r and \n characters from user input before logging.
  2. Consider structured logging (such as JSON), where newlines are less likely to break log parsing.
  3. Validate and sanitize input before writing it to logs.

Configuration

E0118 is enabled by default and has no configuration options.
