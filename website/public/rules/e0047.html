E0047 lifecycle major

Resource lifecycle leak

This rule reports function-scoped resources that are opened and never closed or transferred to another owner. It complements E0043, which reports use-after-close and double-close on tracked streams.

This rule reports function-scoped resources that are opened and never closed or transferred to another owner. It complements E0043, which reports use-after-close and double-close on tracked streams.

Why it matters

Leaving file handles, pipes, process handles, or directory handles open can exhaust system resources, especially in long-running workers or code paths that run many times. Closing resources explicitly, or transferring ownership clearly, makes resource lifetimes easier to reason about.

Bad example

<?php
function write(string $path, string $data): void
{
    $h = fopen($path, 'w');
    fwrite($h, $data);
    // missing fclose($h)
}

Good example

<?php
function write(string $path, string $data): void
{
    $h = fopen($path, 'w');
    if ($h === false) {
        return;
    }
    try {
        fwrite($h, $data);
    } finally {
        fclose($h);
    }
}

What it checks

  • fopen(), fsockopen(), pfsockopen(), stream_socket_client(), and tmpfile() handles that should be closed with fclose()
  • popen() handles that should be closed with pclose()
  • proc_open() handles that should be closed with proc_close()
  • opendir() handles that should be closed with closedir()

The rule scans each function, method, interface method, trait method, and enum method independently. A finding is reported only when the handle is used and stays local to that body: it is not closed, returned, stored in a property or array, passed to a constructor, or passed to a call whose behavior is unknown. Handles that are opened but never used as resources are ignored, because they may be placeholder or discarded results.

Common stream operations such as fread(), fwrite(), fgets(), feof(), fseek(), stream_get_contents(), readdir(), and proc_get_status() are treated as consumers, not ownership transfers. This allows the rule to report a forgotten close even when the handle was used for I/O first.

When it does not report

The rule is intentionally conservative and does not perform alias or reference analysis:

  • Handles stored in arrays, properties, or static properties are treated as transferred, because ownership may be released elsewhere.
  • Handles passed to unknown user functions, methods, or constructors are treated as transferred, because the callee may close them.
  • The rule does not prove that a close runs on every path. A single matching close anywhere in the function is accepted.
  • Reopening the same variable is reported as one finding for the variable, not once per lost handle.
  • Resources created by extensions, such as curl_init(), imagecreate(), or database drivers, are not modeled.
  • Destructors and finally blocks are not interpreted beyond the matching close call they contain.

How to fix

  • Close the handle with the matching function: fclose(), pclose(), proc_close(), or closedir().
  • If ownership moves to another part of the program, return the handle or pass it to a clearly responsible owner.
  • For code with early returns or exceptions, consider a try/finally structure so the close runs on all paths.

Configuration

E0047 has no configuration options and is enabled by default.
