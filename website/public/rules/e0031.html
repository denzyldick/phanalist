Division by Zero

Reports division operations where the divisor can be zero.

Try in Playground All rules GitHub

Reports division operations where the divisor can be zero.

Why it matters

Division by zero causes runtime errors. This rule uses Phanalist's bounded formal verification engine (Z3-backed) to find feasible paths where a divisor can be zero and provide a solver-backed counterexample.

This rule is part of the verification family E0031-E0043. Proofs are relative to the modeled subset, configured checks, and project interprocedural summaries. A clean result means no violation was found in that model; it does not prove every possible PHP execution is safe.

What it does not prove

  • Full PHP semantics. Dynamic features such as eval, reflection, variable variables, dynamic calls and includes, magic methods, and runtime code generation are not modeled.
  • Heap, object-state, reference, and alias invariants beyond the supported function summaries. Nested array shapes are tracked only while they remain unambiguous; a write through an untracked path forgets the affected root array. Reference aliases are not tracked: a tracked array is forgotten when it is shared by reference or iterated by reference, which is conservative but can miss findings. Stream lifecycle tracking is limited to direct fopen(), fclose(), fread(), and fwrite() calls; see E0043.
  • Arbitrary loop invariants. Loops are unrolled to a configured bound; this finds bugs within that bound but does not prove an inductive invariant for all iterations.
  • Arbitrary relationships between the lengths of different arrays. A key from one list is not assumed to index another list even when the source constructs them in parallel. The engine only uses relationships produced by modeled built-ins such as array_diff(), array_map(), and array_merge(), or by explicit guards and assertions.
  • Concurrency and persistent-runtime behavior such as Swoole, RoadRunner, or ReactPHP.
  • Builtin behavior whose result shape depends on an unmodeled flag. For example, count($value, COUNT_RECURSIVE) is not treated as a flat count, and array_slice() preserves list keys only when the flag is absent or provably false.
  • Business, authorization, or security intent. Those properties need to be expressed as assertions or contracts before they can be checked.
  • Properties whose values remain Unknown or unverified. With unknown_policy: report, a loop accumulator that is too unknown to model as a divisor is reported as unverified instead of being claimed safe. A numeric accumulator can still be proven nonzero by a subsequent guard such as $count > 0; a strict guard such as $count !== 0 remains unverified because the accumulator may be an integer or a float.

Bad example

<?php
function average(int $total, int $count): float
{
    return $total / $count; // $count can be 0
}

Good example

<?php
function average(int $total, int $count): float
{
    if ($count === 0) {
        return 0.0;
    }

    return $total / $count;
}

What it checks

  • /, /=, and division inside expressions where the divisor can be zero
  • Literal zero, symbolic zero, and zero reached through tracked arrays or expressions
  • Guarded divisions, including if, switch, match, short-circuit &&, and try/catch/finally paths
  • Loop exit values merged with the feasible zero-iteration path, so a counter initialized before a possibly empty loop is still considered possibly zero
  • Constant-return, identity, and PHPDoc method/function summaries, including inherited and trait methods and imported class names
  • Bounded integer ranges through direct same-class helper calls
  • PHP literal array key rules, including duplicate keys and implicit keys after negative integer keys
  • Exact array_keys() search lengths for tracked arrays passed directly as a variable, inline literal arrays, and simple array_filter() results. Simple arrow functions and single-return closures are modeled as filters; arbitrary callbacks, array_map()/array_values() results, and unknown comparisons fall back to an upper-bound length
  • PHP literal key coercion for array_key() and array_keys(), including bool keys becoming 0/1, float keys being truncated to integers, and null becoming the empty string

Configuration

Each verification code has its own settings block. The relevant check is:

rules:
  E0031:
    php_version: "8.4"
    check_division: true

check_types controls PHPDoc @param/@var refinements. Native PHP type hints are always honoured. php_version is accepted for configuration compatibility; the modelled semantics are the same across PHP 8.0-8.4. loop_strategy: none limits loop bodies to one iteration; every other value uses unroll_depth. unknown_policy: report reports a solver unknown as an unverified finding so it cannot be mistaken for a proof; ignore suppresses that diagnostic.

Each verification code is enabled, disabled, and configured independently. Settings under E0031 apply only to division-by-zero checks; other codes do not inherit them.

Generating regression tests

When test_generation is configured, the solver's parameter values are kept alongside the finding and can be turned into a PHPUnit test:

phanalist --generate-tests tests/phanalist-generated

The test calls the same function with the model's inputs (for example divide(0)) and turns warnings and notices into exceptions, so it fails while the reported path is still reachable and passes once it is fixed. Phanalist only writes the test; running it is up to you and your project's PHPUnit setup. Generation is limited to values that can be written as reliable PHP literals; unsupported inputs are skipped instead of guessed.

Precision and recall benchmark

The supported_fragment_precision_and_recall test runs a labelled corpus of clean and buggy PHP cases through the verification family, then reports precision and recall for the supported fragment. The corpus includes division, modulo, intdiv(), array, string, nullability, return-contract, assertion, unreachable-code, switch, and loop zero-iteration cases. Dedicated benchmark fixtures live in src/rules/examples/e31/benchmark/.

Current result: 49 labelled cases and 50 expected findings, with 0 false positives and 0 false negatives (100% precision and recall). This is a regression benchmark for the supported fragment, not a random sample of arbitrary PHP projects. Run it with:

cargo test supported_fragment_precision_and_recall -- --nocapture

Pinned analyzer reference

The loop fixtures are database-independent: they take an iterable and never open a connection. Compare them with PHPStan 2.3.2, level max, and no baseline. The pinned configuration is src/rules/examples/e31/benchmark/phpstan.neon; run it with the pinned phar:

curl -L -o /tmp/phpstan-2.3.2.phar \
  https://github.com/phpstan/phpstan/releases/download/2.3.2/phpstan.phar
php /tmp/phpstan-2.3.2.phar analyse \
  --configuration=src/rules/examples/e31/benchmark/phpstan.neon \
  --no-progress --error-format=table

PHPStan does not report the division by zero on the feasible zero-iteration path. E0031 reports division-by-zero on the unguarded fixture and no finding on the guarded one.

For the list fixtures, PHPStan 2.3.2 at level max and Psalm 6.20.1 at errorLevel="1" both report the literal -1 access on non-empty-list<int>, but neither reports $items[count($items)] nor the for ($i = 0; $i <= count($items); $i++) access. E0036 reports all three.
